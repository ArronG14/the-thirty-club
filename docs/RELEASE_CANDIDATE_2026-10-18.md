## Production compatibility and release limits

- Six Shopping files (`netlify/concierge/api.ts`, `blobStore.ts`, `shopping.ts`, the Shopping client/API UI and `tools/butler-shopping.mjs`) have identical Git blob IDs between production and candidate. The legacy `/api/concierge/*` entrypoint selects `blobStore()` unless `CONCIERGE_LEGACY_STORAGE=postgres`. Keep that variable blank. Shopping's existing `live/shopping/privilege` record remains in Netlify Blobs; no migration, reset or live claim was attempted. A read-only authenticated production GET must confirm the redeemed state after deployment.
- Membership, Departure Lounge, existing owner rehearsal, Screening Room and Casino code remain present. The candidate adds `/owner`, `/vault`, and `/v/:token`. The Gift Vault room now opens with birthday membership rather than at the provisional 18:00 Jamaica time; individual compartments retain their own server gates.
- The existing Casino frontend still does **not** call the authoritative server play endpoint. Casino-triggered vault release and voucher issuance are not end-to-end live yet. Screening Room content is still an owner content/rehearsal gate.
- The dispatcher behavior intentionally changes: legacy scheduled Departure messages no longer auto-send. The worker runs PostgreSQL approved SMS only when `SMS_SENDING_ENABLED=true`, plus legacy redemption notification retries. The legacy owner console still has manual Send/Copy/Mark sent. Arron must choose a single delivery path for each travel announcement before release; otherwise an expected announcement could be missed. This is a release approval gate, even though the code and tests are deterministic.
- `SMS_SENDING_ENABLED=false` prevents the new PostgreSQL outbox from sending. It does **not** gate the existing Shopping POST's direct Twilio path or the legacy owner's explicit Send now action. Do not exercise those actions as a production smoke test.
